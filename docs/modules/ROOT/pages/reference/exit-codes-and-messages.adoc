= Exit codes and messages
:description: The exit codes of the vulnlog command and the format of its error, warning, and info messages.

The exit codes and the shape of the messages stay stable, so scripts and CI pipelines can rely on them.
The Gradle plugin prints status lines and findings through the Gradle log, and reports failures as Gradle build failures.
For the differences, see xref:reference/gradle-plugin.adoc#differences-from-the-cli[Differences from the CLI].

[[exit-codes]]
== Exit codes

[cols="1,2,4"]
|===
| Code | Meaning | Examples

| `0`
| Success
| The command did its work.
A report or suppression file that lists vulnerabilities is still a success.

| `1`
| General error
| A missing or unknown option or argument, `-q` together with `-v`, `report`, `modify`, or `vex` without a subcommand, a file that doesn't exist or can't be read or written, a file name Vulnlog doesn't accept, or an unexpected error.
Also a release or tag in `modify add` that the file doesn't define, an ID in `modify copy` that the source file doesn't have, `suppress -o` with a selection that covers several reporters, a `--baseline` file that can't be read, or an existing output file for `init` without `--force`.

| `2`
| Validation error
| A Vulnlog file can't be parsed or has validation errors, report inputs have different `project` blocks, `vex openvex` has no statement to write, or an `analysis` contains a character the native suppression format can't hold.

| `3`
| Formatting error
| `vulnlog fmt --check` found a file that isn't in the canonical style.

| `5`
| Invalid option value
| An option of `suppress`, a `report` command, or `vex openvex` names a release or tag the file doesn't know, or a reporter, state, verdict, or disposition that isn't supported.
`--baseline` of `vex openvex` names a file that doesn't exist or isn't an OpenVEX document.
OpenVEX documents tell your customers' tools whether a release is affected by a vulnerability.
|===

Code `4` isn't used.
Each command page lists the codes that command returns.

[[messages]]
== Messages

Every message goes to stderr.
For the output streams, see xref:reference/cli.adoc#stdin[Standard input and output].

A status line reports an action, in the form `<Verb>: <subject>`:

[source]
----
Wrote: vulnlog-impact-report.html
----

The verbs are `Created`, `Wrote`, `Formatted`, `Unchanged`, `Copied`, `Added`, `Updated`, and `Validated`.
`-q` hides status lines.

A finding starts with its level, followed by the file, the location in the file if there is one, and the text:

[source]
----
error: acme-shop.vl.yaml: vulnerabilities[CVE-2021-23337].tags[web]: References undefined tags 'web'. Defined tags: backend, container, frontend, worker
----

A summary line counts the findings of a file, for example `1 error, 2 infos`.
A `hint:` line, indented by two spaces, follows a message when a next step is known.

[cols="1,4"]
|===
| Prefix | Meaning

| `error:`
| The command can't continue.

| `warning:`
| Something is probably wrong, but the command continues.

| `info:`
| Information, for example a release or a tag that no entry uses.

| `hint:`
| What to do next.

| `verbose:`
| Detail about what the command did. Shown with `-v`.

| `debug:`
| More detail, for bug reports. Shown with `-vv`.
|===

`error:`, `warning:`, and `info:` print at every verbosity.
The exception is `info: no fixed vulnerabilities to report` of `report changelog`, which `-q` hides.

A usage error, such as an unknown option, a missing argument, or a file that doesn't exist, exits with `1`.
It prints the `Usage:` line of the command, a blank line, and a line that starts with `Error:`:

[source]
----
Usage: vulnlog validate [<options>] <inputs>...

Error: missing argument <inputs>
----

Because the prefixes of the other messages stay the same, `grep '^error:'` finds every error except usage errors.

An unexpected error prints one `error:` line.
With `-vv`, the command also prints the stack trace.

== Colour

Messages are coloured when stderr is a terminal, and plain when it's piped or redirected.
`NO_COLOR`, set to any value, turns colour off.
`FORCE_COLOR` turns it on, for example in CI systems that show ANSI colours, such as GitHub Actions.
`NO_COLOR` takes precedence when both are set.

Colour never carries information on its own.
Plain output contains the same text.
