= vulnlog vex openvex

NOTE: The Vulnlog OpenVEX export feature is currently incubating. Its behavior and configuration options may change in the upcoming releases.

Writes an https://github.com/openvex/spec[OpenVEX] document from your Vulnlog file.
Hand it to Trivy or Grype and the findings you triaged disappear from the scan, for you and for everyone who scans your software.

[source]
----
vulnlog vex openvex <file> [--release <release-id>] [--tag <tag>]... [--baseline <path>] [-o <path>]
----

[cols="2,3"]
|===
| Flag | Description

| `--release <release-id>`
| Write the document for this release only.
Without it the document covers every release that declares `purls`.
See <<scoping>>.

| `--tag <tag>`
| Keep only the release purls carrying this tag.
Repeatable; a purl carrying any of the given tags is kept.
See <<scoping>>.

| `--baseline <path>`
| The OpenVEX document you published before.
Its `@id` is kept and its `version` counts up when the content changed.
See <<identity>>.

| `-o, --output <path>`
| Output file path, or `-` to write to stdout.
Defaults to `vex.json` in the current directory.

| `-`
| Use as the file argument to read from stdin.
|===

[[purls]]
== Declare release purls

A statement names the products it applies to, so every release the document should cover needs `purls`: the https://github.com/package-url/purl-spec[Package URLs] of the artifacts you ship.
Tag them when you ship more than one kind of artifact.

[source,yaml]
----
releases:
  - id: 1.2.0
    published_at: 2026-04-20
    purls:
      - purl: "pkg:maven/com.acme/acme-web-app@1.2.0"
        tags: [ library ]
      - purl: "pkg:oci/acme-web-app?repository_url=ghcr.io/acme/web-app"
        tags: [ container ]
----

Declare the purl your users' scanner matches:

[cols="1,2,1"]
|===
| Artifact | Release purl | Matched by

| Container image
| `pkg:oci/<name>?repository_url=<registry>/<repo>`
| Trivy, Grype

| Library or plugin
| The ecosystem purl, for example `pkg:maven/com.acme/acme-lib@1.2.0`
| Trivy, also in the scans of your users

| Application scanned as a project
| The purl of the root module, for example `pkg:maven/com.acme/acme-web-app@1.2.0`
| Trivy

| Native binary, installer
| `pkg:generic/<name>@<version>`
| No scanner filters on it yet.
|===

A release without `purls` is left out of the document and named in a `warning:` line; `vulnlog validate` warns about it as well.

[[status]]
== What a statement says

Vulnlog writes one statement per vulnerability entry and release it applies to.
An entry applies from the earliest release it lists through every later release in the file.
From the release named by `resolution.in` on, it is `fixed`, even where `releases` lists it too.

[cols="1,3"]
|===
| Your entry | OpenVEX statement

| No verdict yet
| `under_investigation`, with `analysis` as `status_notes`.

| `not affected`
| `not_affected`, with the `justification` and `analysis` as `impact_statement`.

| `affected`
| `affected`, with `analysis` as `status_notes` and an `action_statement`, see below.

| `resolution.in` and later releases
| `fixed`, without `analysis`: it describes the state before the fix.
|===

The `action_statement` follows from `disposition` and `resolution.in`, never from `analysis` or the resolution `note`, which are written for your team:

[cols="1,1,2"]
|===
| `disposition` | `resolution.in` | `action_statement`

| _(absent)_ or `will fix`
| set
| `Update to release <id>.`

| _(absent)_
| absent
| `No remediation is available yet.`

| `will fix`
| absent
| `A fix is planned but not yet available.`

| `wont fix`
| set
| `The risk is accepted for this release. A fix ships with release <id>.`

| `wont fix`
| absent
| `The risk is accepted. No fix is planned.`
|===

Each statement is dated by the day its status became true: `resolution.at`, else the fix release's `published_at`, for `fixed`; `analyzed_at` for a verdict; the earliest `reports[].at` for an open investigation or a verdict without `analyzed_at`.
Without any of these the release's own `published_at` is used, and without that the time of the run that first issues the statement.
`vulnlog validate` warns about undated statements, because only a `--baseline` keeps such a time from one version to the next.

`aliases`, `description` and `packages` are written as well; `packages` become the subcomponents of each product.
`name`, `severity`, `comment`, `reports` and `tags` have no place in OpenVEX.

[[scoping]]
== One document per release and artifact

Without scoping flags the document covers every release that declares `purls`.
That suits your own CI scan and a VEX hub, where one file serves every release.

To publish next to an artifact, write one document per release and artifact: `--release` picks the release and `--tag` picks its purls.

[source]
----
vulnlog vex openvex vulnlog.yaml --release 1.2.0 --tag container -o vex-1.2.0-container.json
----

`--release` does not cut the range: an entry reported for an earlier release still applies, and a fix in a later release is still named in the `action_statement`.
Unlike on the other commands, `--tag` selects release purls here, not vulnerability entries.

[[identity]]
== Keep a published document stable

Consumers recognise later versions of a document by its `@id`.
Without `--baseline` every run issues a new `@id` with `version` `1`, even when the output file exists.
With `--baseline`, the run continues the document you published:

[source]
----
vulnlog vex openvex vulnlog.yaml --baseline vex.json -o vex.json
----

* `@id` stays, `version` counts up and `timestamp` is the time of the run.
* A statement that did not change keeps its time.
* When nothing but the clock would change, no new version is issued: writing back to the baseline prints `Unchanged:`, and any other output receives the baseline as it is.
* A baseline written by another tool always counts as changed, because it carries fields Vulnlog does not write.

A baseline that is missing, no OpenVEX document, in another OpenVEX version than `0.2.0`, or has an `@id`, `timestamp` or `version` that cannot be continued fails the run.
Vulnlog never replaces it with a new identity, because consumers following the `@id` would lose track of your document.

== Use the document with your scanner

Only `not_affected` and `fixed` statements remove a finding; `affected` and `under_investigation` keep it in the scan.

[source]
----
trivy image --vex vex.json ghcr.io/acme/web-app:1.2.0
trivy fs --vex vex.json --show-suppressed .
grype --vex vex.json ghcr.io/acme/web-app:1.2.0
----

Trivy matches a product against the scan target and every dependency in its tree, so a library's document also filters the scans of its users.
Grype matches the scanned image only and needs a `pkg:oci` purl.

== When the command fails

* The Vulnlog file fails validation: exit `2`.
* No statement applies, because no release declares `purls`, no entry references one that does, or the scope leaves nothing: exit `2`, no file is written, since OpenVEX requires at least one statement.
* An unknown `--release` or `--tag`, or a `--baseline` that cannot be continued: exit `5`.

See xref:reference/exit-codes-and-messages.adoc[Exit codes and messages] for the full table.
