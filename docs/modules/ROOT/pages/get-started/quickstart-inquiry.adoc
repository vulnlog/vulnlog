= Answer a vulnerability inquiry
:description: Tutorial: answer a customer who asks whether your product is affected by a vulnerability, with the analysis in the Vulnlog file.

In this tutorial, you answer a customer who asks whether Acme Shop is affected by a vulnerability.
You find the team's assessment in the Vulnlog file and turn it into an answer, without analysing the vulnerability again.
It takes about 5 minutes.

The customer writes:

____
Our scanner flags CVE-2024-3094, the XZ Utils backdoor, in the Acme Shop 4.3.0 container image.
Are we affected?
____

== Before you start

You don't need the Vulnlog CLI.

* Make sure the `grep` command is available. Linux and macOS include it, but Windows doesn't by default.
* Create an empty directory and save the Acme Shop Vulnlog file in it as `acme-shop.vl.yaml`:
+
.acme-shop.vl.yaml
[%collapsible]
====
[source,yaml]
----
include::example$acme-shop.vl.yaml[]
----
====

Run every command in this tutorial from the directory that contains `acme-shop.vl.yaml`.

== Find the entry

Search the file for the identifier the customer gave you:

[source,bash]
----
grep -n "CVE-2024-3094" acme-shop.vl.yaml
----

[source]
----
56:  - id: CVE-2024-3094
----

The entry starts on line 56.
Open the file in your editor and go to that line.

A customer's scanner sometimes uses a different identifier for the same vulnerability.
The `aliases` field of an entry lists the other identifiers, and a search finds them too.
For example, search for `GHSA-jfh8-c2jp-5v3q`, the alias of Log4Shell:

[source,bash]
----
grep -n "GHSA-jfh8-c2jp-5v3q" acme-shop.vl.yaml
----

[source]
----
140:    aliases: [GHSA-jfh8-c2jp-5v3q]
----

== Read the assessment

The entry for `CVE-2024-3094` reads:

[source,yaml]
----
include::example$acme-shop.vl.yaml[lines=56..71]
----

Read the fields that matter for your answer:

* `releases` is `[4.3.0]`, the release the customer runs.
* `packages` names the affected package as a package URL (PURL), a standard way to name a package, its ecosystem, and its version in one string.
Here it's version 5.4.1 of the Debian package `xz-utils`.
* `tags` is `[container]`, so the assessment is about the container image, which is what the customer scans.
* `verdict` is `not affected`.
This is the team's answer to the customer's question.
* `justification` is `vulnerable code not present`.
This value comes from a fixed list that VEX uses.
VEX (Vulnerability Exploitability eXchange) is a standard way to tell others whether a vulnerability affects a product.
* `analysis` is the team's reasoning, in words you can pass on: the image ships xz-utils 5.4.1, and the backdoor is only in 5.6.0 and 5.6.1.
* `analyzed_at` is the date of the analysis, 2 July 2026.

The `reports` field shows that the team first heard of this vulnerability through a customer inquiry on 2 July 2026.
The team analysed it the same day, so you can answer now without new work.

== Write the answer

Base every statement on a field of the entry:

____
Thank you for your question.
Acme Shop 4.3.0 isn't affected by CVE-2024-3094.
The container image is based on Debian 12, which ships xz-utils 5.4.1.
The backdoor is only in the upstream releases 5.6.0 and 5.6.1, so the vulnerable code isn't present in the image.
Our security team completed this analysis on 2 July 2026.
____

== What you've learned

Now you can:

* Find an entry by its identifier or one of its aliases.
* Check that an assessment covers the customer's release.
* Base an answer on the verdict, justification, and analysis of an entry.
